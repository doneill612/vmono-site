## What vmono guarantees

- A source repo's working tree and checked-out branch are never touched. Only the branches sessions work on move. Starting a session fetches every member's source first, which updates its remote-tracking branches and prunes those deleted on the remote; it moves no local branch.
- A dirty worktree is never removed without `--force` (or typing the package or session name in the TUI). Removing a member, deleting a session or deleting a package checks every session it reaches, and one dirty worktree refuses the whole operation.
- A branch with work that is not merged is never deleted, even with `--force`. A branch vmono made that nothing was committed to, and that is on no remote, is deleted with its worktree. `--delete-branches` also deletes branches whose work is on their base: their commits themselves, a copy of each (a rebase merge), or one commit making the same change (a squash merge). vmono establishes that by comparing changes, so a squash merge leaves the branch's own commits behind when it goes; their content is on the base, and git keeps them in the reflog for a while. A merge that cannot be recognized keeps the branch.
- Removing a worktree is refused when commits made on a detached HEAD are on no branch. Commits on a branch stay with the branch.
- `vmono session push` is the only command that pushes, and only on request. It sends one branch per member, the one the session works on, never forced, and never to the branch it is meant to merge into. A remote branch that moved on or was deleted is left alone. A session [built on a local branch](/docs/starting-a-session#what-a-new-branch-starts-from) with unpushed commits publishes those with its own.
- `vmono session update` never rewrites commits that have been pushed.
- Looking at a session (`status`, `session ls`, `review`) moves no branch in a source repo and adds no objects to it.
- Deleting a package or session directory by hand leaves its worktrees registered in the source repos. `vmono doctor --fix` prunes those records, and starting a session and adding or editing members release any whose directory is gone before adding a worktree, warning about each. Branches are still kept, so recreating a session of the same name asks to reuse its branch. Prefer `vmono session rm` and `vmono delete`, which remove the worktrees properly.
- On Windows, vmono refuses to remove a session, member or package while your working directory is inside it, since Windows cannot delete a directory in use. `cd` out and run the command again, naming the session (`vmono session rm PKG/SESSION`). Nothing has changed when it refuses, and `--force` does not apply. Another program holding the directory open, such as an editor or a second terminal, can still make the removal fail with git's own `Permission denied`.
- Hooks and `setup` and `teardown` commands run as you, outside any sandbox the harness uses. They come only from your config and the package manifest, and one an agent suggested joins the manifest only when you accept it, so treat a change to those like a change to a script. See [Setup and hooks](/docs/setup-and-hooks).
- Symlinks are never followed or created.
- [`vmono package init`](/docs/package-init) works in temporary detached worktrees. One whose files were changed is kept until you discard it with `--clean --force`.
- Committing from a worktree writes into the source repo's git directory, outside the package. `vmono inspect --json` lists each `git_common_dir` so sandboxing wrappers can allow it.

## What your harness enforces

vmono enforces nothing about what an agent may do; the harness's own permission system does. The `claude-code` and `opencode` adapters add `ask` rules for `vmono rm`, `vmono session rm`, `vmono session push`, `vmono edit` and `vmono delete` and a deny rule for edits under `_ref/`. They allow, without asking, the commands that only read or display: `vmono show`, `status`, `ls`, `repos`, `path`, `inspect`, `session ls`, `session review`, `integration ls` and `print`, `doctor` (without `--fix`) and `--version`. Claude Code evaluates `ask` before `allow` whatever the specificity, so a command that asks cannot be exempted for a flag such as `--dry-run`; that is why the read-only form of `session push` is the separate `session review`. Codex and Pi get no permission rules from vmono: there, the skill's instruction to push only when you ask is all there is, beyond the harness's own settings. A rule in a member's own settings that asks about or denies one of the allowed commands still wins.
